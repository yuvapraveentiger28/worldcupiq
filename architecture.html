PK,FK in the diagram means that column is part of a composite primary key and a foreign key at the same time (e.g. passing_edge's four-column key) — Mermaid's own key syntax only cleanly renders one marker per column, so composite PK+FK columns are called out this way instead of silently picking just one. match_prediction_feature.feature_01_to_65 stands in for the real 65 ML feature columns (see the Cluster G detail below) — listing all 65 in the diagram itself would drown out everything else.

Decisions made while going from 8 tables to 28 — flag anything you'd change

  1. Restored tournament. The 8-table pass dropped it for "single-tournament scope" — that broke the moment historical entered the picture. hist_tournaments covers 1930–2022; a seeded 2026 row extends it. team, player, match are now conformed across every tournament, not siloed as "2026" vs "historical" copies — that's what README §6 asks for ("historical facts conform to the same dims").
  2. Moved group_name off team onto a new team_tournament bridge. A team's group changes every tournament; it isn't a team attribute once team spans eras. Also absorbs hist_team_appearances.
  3. No standalone country or host_country table. In this domain a World Cup "team" essentially *is* a country — a separate country table would mostly just mirror team 1:1. Used inline country_code on team / venue instead; the host nation's name lives on tournament.host_country_name, and hist_host_countries' real shape (host team + how they performed, not geography) turned out to belong on tournament_standing.host_performance instead — corrected after the first pass of this tab claimed a host_country table that was never actually built.
  4. Merged hist_referee_appearances + hist_referee_appointments into one match-grain referee_assignment (role: main / assistant / VAR) — appointment vs. appearance was a tournament-panel-vs-match-day distinction that collapses cleanly to "who officiated this match, in what role."
  5. Merged hist_manager_appearances + hist_manager_appointments into one tournament-grain manager_appointment — same reasoning. No 2026 manager data exists in any current bronze source, so this cluster is historical-only for now.
  6. match_player_physical and match_goalkeeper split out from match_player — GPS/physical tracking and goalkeeper-specific measures (team_goal_prevention, team_goalkeeping_distribution) are different grains/availability than general on-ball player stats, so folding them into match_player would mean mostly-null columns for outfield players and non-starters.
  7. match_prediction_feature kept separate from prediction. relational.match_prediction_features (originally estimated at 65 anonymous ML input features, mominullptr; verified after landing as 10 real named home_*/away_* columns) and predictions.pre_match_prediction (Onside Arena's actual output probabilities) are different things from different sources at the same grain — inputs vs. output, not duplicates.

Caveat resolved — verified against real data

  1. The above was originally written before Phase 1 landed any source file, as a best-reasonable-naming placeholder. All 60 bronze tables have since landed and every silver table was rebuilt in ingestion/lakeflow/silver.py against the real, verified column names — checked directly via databricks tables get against the actually-landed data, not guessed. A few real shapes differed from this original review (see the file header in silver.py for the specifics, e.g. match_prediction_feature's real ~60 named home_*/away_* columns replacing the anonymous feature_01..65 placeholder guessed here). The grain/keys design below held up; only the column-name guesses needed correcting.

Gold — data model Built

16 tables — 6 dimensions + 10 facts — star-schema'd from the 27 Silver tables for BI/semantic consumption. ingestion/lakeflow/gold.py is deployed as gold_pipeline and has run successfully end to end against real Silver data — all 16 flows completed. Colored by role: dimensions, match-grain facts, and tournament/group-grain facts.

3 real bugs found by actually running it — schema corrected to match

  1. dim_team — country_code doesn't exist. silver.team never actually carries one (no clean source column on relational.teams); the review design assumed it would. Column dropped.
  2. fact_pass — xt_added doesn't exist. silver.passing_edge never computed an expected-threat model; it was a documented aspiration in the Silver review that was never actually built. Column dropped (silver's own PASSING_EDGE diagram corrected too).
  3. fact_team_match — ambiguous home_away reference. Both the derived home/away split (from silver.match) and silver.match_team's own home_away column survived a join keyed only on [match_id, team_id] — same class of bug as the one found building Silver's team() table. Fixed by dropping match_team's copy before joining.

Decisions made drafting this — flag anything you'd change

  1. 9 of the 27 Silver tables are not carried into Gold v1 — qualified_team, squad_member, referee, referee_assignment, manager, manager_appointment, award, award_winner, match_prediction_feature. None of the 5 demo questions need officiating, coaching, qualification-route, roster, or ML-feature detail at the BI grain — full detail on all of them stays queryable directly against Silver. See the mapping table below for the per-table reasoning.
  2. Added fact_group_standing and fact_prediction — neither was in the original README §6 blueprint, but both map cleanly from Silver tables that already exist (group_standing, prediction) and both are directly useful: group tables are a natural BI query, and fact_prediction is what README §9's "prediction/surprise analysis" demo beat needs.
  3. team_tournament and tournament_standing both fold into fact_team_tournament instead of becoming two separate gold facts — in the real Silver build they ended up as near-duplicate sources of the same team-per-tournament grain (group/rank from one, final_rank/host_performance from the other), so Gold consolidates rather than carrying the duplication forward.
  4. Merged the 4 original blueprint's event facts into one fact_match_event and split out fact_goalkeeper_match — same two simplifications flagged when this list was first proposed, now reflected in the diagram.

  1. UC Metric View joins are single-hop from source only — a join's on: clause can't reference another join's alias. Chaining dim_tournament/dim_stage/dim_venue off the already-joined gold.fact_match alias failed with UNRESOLVED_COLUMN. Since tournament_id/stage_id/venue_id live only on fact_match, not on the match-grain fact tables themselves, the 3 match-grain views expose those as raw IDs rather than resolved names (no tournament_year, stage_name, venue_name in those three) — resolve them downstream instead.
  2. goalkeeper_match_performance.player_name was null on every row — traced to gold.fact_goalkeeper_match.player_id being null on all 208 rows, itself traced to silver.match_goalkeeper never resolving a starting keeper's identity. Fixed in silver.py's match_goalkeeper() (join to match_appearances' starting GK per match_team_id), redeployed through silver_pipeline → gold_pipeline, reverified live — e.g. Jordan Pickford now resolves correctly with 18 saves.

2 real findings from actually building this

  1. The Ontology Wizard couldn't wire relationships for every entity it created. Of the 16 auto-generated entities, 7 came out completely disconnected — Player, Stage, and the 5 measurement/performance facts (Team Match Performance, Player Match Performance, Goalkeeper Match Performance, Passing Edge, Team Tournament Performance, Team Dominance Score). The entities themselves were correctly sourced from real tables; the LLM just didn't finish drawing edges to them. Fixed by manually specifying and adding 25 additional relationships (listed below), each name kept globally unique per OntoBricks' constraint that a relationship name can't be reused across different entity pairs (e.g. teamMatchStatsForTeam / playerMatchStatsForTeam / gkMatchStatsForTeam instead of three forTeams).
  2. Node/attribute mapping in the Visual Mapping Designer is slow and strictly one-at-a-time. Despite OntoBricks' own docs describing an "Auto-Map" step ("LLM generates SQL mappings for every entity and relationship") as part of a 4-click automated pipeline, mapping in practice requires clicking through each entity and relationship individually to configure its data mapping — no bulk-apply observed for a graph this size (16 entities, 30+ relationships). Budget real time for this step; it's the current bottleneck, not domain setup or ontology generation.

3 bugs found and fixed in OntoBricks itself while standing this up

  1. get_table_comment() used psycopg-style %s placeholders against a databricks-sql-connector cursor, which requires ? — every table-comment lookup failed with PARSE_SYNTAX_ERROR, silently reported as "0% table descriptions" even though the comments existed in UC. Same bug found and fixed in probe_schema_has_tables().
  2. check_table_select_permission() ran SELECT * FROM … LIMIT 0 as its access probe — star-expansion against a Unity Catalog Metric View pulls in measure columns unwrapped, which fails with METRIC_VIEW_MISSING_MEASURE_FUNCTION even under LIMIT 0, showing as a false "permission denied" on all 5 semantic views. Fixed by projecting a literal (SELECT 1 …) instead, which still exercises the SELECT grant without touching any column. Same fix applied to the identical probe in Mapping.py's relationship-mapping permission check.
  3. The SQL Warehouse ID silently pointed at a warehouse that no longer existed (.env had the right ID; a stale ID was persisted separately in OntoBricks' own "stored globally" app config) — catalogs hung forever loading with no error logged, since the SDK call never resolved against a nonexistent resource. Fixed by re-selecting the warehouse through OntoBricks' own Databricks settings screen.
